critical Missing empty-share-supply bootstrap in convert_assets_to_shares permanently bricks all deposits once a vault reaches shares == 0 with assets > 0

rule rule_fee_deposit_bricked_when_share_supply_is_zero in fee_based_deposits.rsprover run

`Vault::convert_assets_to_shares` has no special case for an empty share supply: when `vault.shares == 0` and `vault.assets > 0` it computes `mul_div_floor(net_amount, 0, assets) == 0` for every possible deposit amount, so `mint_shares(0)` always trips `require_gt!(amt, 0)`. The Certora satisfy rule `rule_fee_deposit_bricked_when_share_supply_is_zero` was refuted — no deposit amount at all can mint shares on such a vault — and the state is permissionlessly reachable by donating one asset token and calling `process_update_reward`, after which deposits are dead forever and the donated assets are unrecoverable because no shares exist to burn.

Severity rationale
Impact high × Likelihood high — The Prover exhaustively refuted the existential over all `u64` deposit amounts, proving the deposit path is dead — not merely hard to use — on any vault with zero shares and positive assets, and the stranded assets are unrecoverable because no shares exist to burn. Reaching that state requires no privilege: any actor can transfer one asset token to the vault's asset PDA and call the permissionless `process_update_reward`, which increases `assets` via `add_token` without minting shares. The only precondition is a vault at `shares == 0`, which is the natural state of every newly created or fully-exited vault.
Impact
Permanent denial of service on the vault plus permanently frozen assets. Once a vault is in `shares == 0 && assets > 0`, every deposit through `process_deposit_with_fee` fails the `require_gt!(amt, 0)` guard in `mint_shares` for every possible amount, and `process_deposit_with_fee_exact` fails with `MathOverflow` because `convert_shares_to_assets` divides by a zero share supply. The vault can never again accept a deposit, and since no shares exist, there is nothing to burn to withdraw the assets sitting in the asset account — the donated/accrued assets are stranded with no recovery path. An attacker can inflict this on a fresh or fully-exited vault for the cost of a single asset token and one permissionless instruction call.
Description
The rule `rule_fee_deposit_bricked_when_share_supply_is_zero` is an existential (`cvlr_satisfy!`) property: for an otherwise unconstrained `Vault` with `v.shares == 0`, `v.num_assets() > 0` and `u64::from(v.fee_bps) < 10000`, it asks the Prover to exhibit *any* `amount: u64` for which `crate::operations::vault_deposit_assets_with_fee(&mut v, amount)` succeeds and yields `shares_to_user > 0`. The Prover returned no witness, which for a satisfy rule is the refutation itself: over the entire `u64` range of deposit amounts, no execution mints a positive number of shares. The causal chain is fully contained in the accounting core — the rule drives a pure `&mut Vault` transition with no accounts, no `Context`, no CPI, no PDA derivation, and no mocked or havoced symbol on the path, so the defect cannot be attributed to harness plumbing: 1. `vault_deposit_assets_with_fee` (`programs/vault/src/operations/vault_fee_operations.rs`) calls `vault.fee_in_bps()`, which succeeds because `FeeBps::try_from` only rejects values above `10000`. It then computes `net_amount = amount - floor(amount * fee_bps / 10000)`, which is well defined and ranges over essentially all of `u64`. 2. `Vault::convert_assets_to_shares` (`programs/vault/src/state.rs`) special-cases only `num_shares() == num_assets()`. With `shares == 0` and `assets > 0` that shortcut is not taken, so control falls through to `mul_div_floor(net_amount, num_shares(), num_assets()) = floor(net_amount * 0 / assets) = 0`. Multiplication by a zero share supply annihilates the operand, making the result a function of the pre-state alone — quantifying over every `amount` buys nothing. 3. `vault.mint_shares(0)` hits `require_gt!(amt, 0, VaultError::GuardFail)` and returns `Err`. Both conjuncts are therefore jointly unreachable: `ok` is always false and `shares_to_user` is always `0`. The vault fields the rule left free (`admin`, mints, bumps, `fee_amount`) are never read on this path and so cannot be what blocks the witness. The symmetric gap exists on the other side of the conversion: `convert_shares_to_assets` and `convert_shares_to_assets_ceil` divide by `num_shares()`, so on the same `shares == 0` state they return `MathOverflow`. This makes `process_deposit_with_fee_exact` fail as well, and it means no redemption-style path can be used to extract the stranded assets either. (This second half follows from reading the source — the refuted rule only drives `vault_deposit_assets_with_fee` — but it is a direct consequence of the same missing bootstrap case.) Crucially, the bricking state is not merely hypothetical: it is permissionlessly reachable. An attacker transfers a single asset token into the vault's asset PDA and invokes the permissionless `process_update_reward`, whose `vault_update_reward` calls `add_token(reward)` and increases `assets` without minting any shares. On a fresh or fully-exited vault (`shares == 0`), this moves the vault into `shares == 0 && assets > 0` — the exact pre-state the Prover proved admits no successful deposit. The remediation is to add an empty-share-supply bootstrap to the conversion arithmetic: when `num_shares() == 0`, a deposit should mint shares one-for-one against the net assets contributed rather than computing `floor(token * 0 / assets)`, and `convert_shares_to_assets`/`convert_shares_to_assets_ceil` need a consistent empty-supply case so they do not divide by zero. Because a plain one-for-one bootstrap hands any previously donated assets to the first depositor (the classic inflation-attack surface), it should be paired with a virtual-shares/virtual-assets offset applied inside both conversions, or a minimum initial deposit whose shares are minted to the program. Separately, it is worth gating `process_update_reward` on a vault with no outstanding shares, since in that configuration there is no holder for the reward to accrue to.
Attack path
1. Identify a vault with `shares == 0` — i.e. any newly initialized vault before its first deposit, or one from which all shares have been redeemed. 2. Transfer a single asset token into the vault's asset PDA token account. 3. Call the permissionless `process_update_reward` instruction. Its `vault_update_reward` invokes `add_token(reward)`, raising `vault.assets` above zero without minting any shares. 4. The vault is now in `shares == 0 && assets > 0`. Any subsequent `process_deposit_with_fee` call computes `net_amount = amount - fee`, then `convert_assets_to_shares(net_amount) = mul_div_floor(net_amount, 0, assets) = 0`, and `mint_shares(0)` reverts on `require_gt!(amt, 0, VaultError::GuardFail)` — for every amount, as the refuted satisfy rule proves. 5. `process_deposit_with_fee_exact` is dead on the same state because `convert_shares_to_assets(0)` divides by `num_shares() == 0` and returns `MathOverflow`. 6. No shares exist, so no redemption can move the donated assets out. The vault is permanently unusable and the assets are permanently stranded.
Assumptions & uncertainties
The refutation is direct evidence only for `vault_deposit_assets_with_fee`, the accounting core of `process_deposit_with_fee`; the rule never calls `vault_deposit_assets_with_fee_exact` and never exercises handler-level account plumbing. The claim that the `_exact` variant is likewise dead on this state (via `convert_shares_to_assets` dividing by `num_shares() == 0`) is derived from reading `programs/vault/src/state.rs`, not from this Prover run. Likewise, the reachability step via donating one asset token plus a permissionless `process_update_reward` / `vault_update_reward` → `add_token(reward)` is taken from source reading rather than being produced by this rule, which starts from a `nondet_vault()` pre-state; it assumes `process_update_reward` is in fact callable by an unprivileged signer and does not itself reject vaults with zero outstanding shares. If some other instruction or initialization invariant prevents a vault from ever holding assets while `shares == 0`, the likelihood drops, but the arithmetic defect in the conversion functions remains.

The Prover refuted the liveness property that some `amount` makes `process_deposit_with_fee` mint positive shares — every deposit fails at `mint_shares`'s `require_gt!(amt, 0)` guard. Severity rationale
Impact high × Likelihood high — The counterexample lies inside the property's plain domain (positive assets, legal fee_bps, positive amount) and shows the deposit core returning Err regardless of amount, so the break is unconditional on that pre-state. The pre-state itself is reachable by any unprivileged actor on a freshly created vault at the cost of one asset token plus a call to the permissionless `process_update_reward`, and the result — all deposits permanently reverting with no way to burn shares and recover the assets — is a permanent freeze of the vault and its balance.
Impact
Permanent denial of service on an affected vault plus stranded funds. Once a vault is in the `shares == 0 && assets > 0` state, every call to `process_deposit_with_fee` reverts at `mint_shares`'s `require_gt!(amt, 0)` guard for any deposit amount, and `process_deposit_with_fee_exact` reverts with MathOverflow via division by a zero share supply. No shares exist that could be burned, so the assets held by the vault's asset PDA — the attacker's donation and anything else accrued — are unrecoverable through normal vault operations. The vault is effectively dead and must be redeployed.
Description
The rule `rule_fee_deposit_bricked_when_share_supply_is_zero_witness` builds an unconstrained `Vault`, forces `v.shares = 0`, and assumes only three things inside the property's stated domain: `v.num_assets() > 0`, `u64::from(v.fee_bps) < 10000`, and `amount > 0`. It then drives the program's own accounting core `crate::operations::vault_deposit_assets_with_fee(&mut v, amount)` and asserts `ok && e.shares_to_user > 0`. The counterexample (programs/vault/src/certora/specs/fee_based_deposits.rs:771) shows `a0 = v.num_assets() = 2^64 - 1`, `v.shares = 0`, `fb = v.fee_bps = 9999` (a legal rate strictly below the 10000 cap), and `amount = 2^64 - 1` — the largest expressible deposit, so the failure cannot be blamed on a too-small request. The logged effect is `s = 0, a = 0, f = 0` with `o = ok as u64 = 0`: the call returned `Err` and the zeros are `unwrap_or_default()` filler, not computed amounts. The assertion fails on its first conjunct. The causal chain is fully visible in the source: 1. `vault_deposit_assets_with_fee` (`programs/vault/src/operations/vault_fee_operations.rs`) calls `vault.fee_in_bps()?`, which succeeds because `FeeBps::try_from`'s `require_le!` accepts 9999. It computes `net_amount = amount - floor(amount * 9999 / 10000)`, a strictly positive net. 2. It calls `vault.convert_assets_to_shares(net_amount)`. In `Vault::convert_assets_to_shares` (`programs/vault/src/state.rs`) the only shortcut is `num_shares() == num_assets()`, which does not apply (`0 != 2^64 - 1`). Control falls through to `mul_div_floor(net_amount, self.num_shares(), self.num_assets())` = `floor(net_amount * 0 / assets)`, which is 0 for every possible `net_amount` — multiplying by a zero share supply annihilates the operand. 3. `vault.mint_shares(0)` then trips `require_gt!(amt, 0, VaultError::GuardFail)` and returns `Err`. Because `shares_to_user` is a function of the pre-state alone once `num_shares() == 0`, no choice of `amount` escapes: the fee-deposit path is not merely hard to hit on this state, it is unreachable. The rule drives a pure `&mut Vault` transition with no accounts, CPI, PDA derivation, or summarized symbols on the path, so the result is not an account-model or havoc artifact — every logged value is reproducible by hand from the two functions. By source inspection (not exercised by this trace), the same pre-state also kills the `_exact` variant: `convert_shares_to_assets` / `convert_shares_to_assets_ceil` compute `mul_div_floor(shares, assets, num_shares())`, which divides by zero and yields `MathOverflow` when `num_shares() == 0`. Fixing only the assets-to-shares direction would leave that second route broken. The `shares == 0 && assets > 0` configuration is reachable permissionlessly: `vault_update_reward` calls `add_token(reward)` and mints no shares against it, so anyone can transfer a single asset token into the vault's asset PDA and invoke the permissionless `process_update_reward` on a fresh vault. After that, every `process_deposit_with_fee` fails at `mint_shares(0)`, and because no shares exist, no one can burn shares to withdraw the donated assets. Remediation belongs in `Vault::convert_assets_to_shares` and `convert_shares_to_assets`/`convert_shares_to_assets_ceil`: add an empty-supply case so a deposit into a zero-share vault mints shares against the net assets contributed instead of `floor(token * 0 / assets)`, and handle `num_shares() == 0` in the reverse direction so it does not divide by zero. Note that a naive one-for-one bootstrap hands any previously donated assets to the first depositor (the classic ERC-4626 inflation-attack surface); a virtual-shares/virtual-assets offset applied consistently in both directions, or a minimum initial deposit whose shares are minted to the program, is the standard mitigation. Separately, it is worth gating `process_update_reward` so it cannot be invoked by anyone on a vault with no outstanding shares, since in that configuration there is no holder for the reward to accrue to.
Attack path

The attacker calls the permissionless `process_update_reward`. `vault_update_reward` calls `add_token(reward)`, increasing `vault.assets` while minting no shares, leaving `shares == 0 && assets > 0`. 4. Any honest user now calls `process_deposit_with_fee` with any `amount > 0` (the counterexample uses `amount = 2^64 - 1`, `assets = 2^64 - 1`, `fee_bps = 9999`). `convert_assets_to_shares` evaluates `mul_div_floor(net, 0, assets) = 0`, and `mint_shares(0)` fails `require_gt!(amt, 0)` — the call returns `Err` (`o = 0` in the trace). 5. `process_deposit_with_fee_exact` on the same state fails with MathOverflow because `convert_shares_to_assets` divides by `num_shares() == 0`. 6. No shares exist to burn, so the donated assets cannot be withdrawn and the vault is permanently unusable.

The claim that the `_exact` variant is dead on the same state (via `convert_shares_to_assets` dividing by `num_shares() == 0`) and the claim that `process_update_reward` / `vault_update_reward` can create the `shares == 0 && assets > 0` state permissionlessly both follow from reading the source as reported in the analysis, not from this counterexample. Severity assumes vaults can exist in a pre-first-deposit state exposed to the permissionless reward-update path.

high DepositWithFeeContext never re-derives the vault's shares-mint (or vault-assets) PDA, accepting attacker-substituted mint and asset accounts

rule rule_fee_deposit_does_not_rederive_shares_mint_pda in fee_based_deposits.rsprover run

`DepositWithFeeContext::validate` validates `shares_mint` and `vault_assets_account` only by comparing them to fields read out of the caller-supplied `Vault` account, and never re-derives the canonical PDAs the way `DepositContext::validate` does via `VaultSharesMint::check_vault`. The Prover produced a concrete execution in which `load` returns `Ok` for a shares-mint account that is not the program-derived address, so the fee-deposit handlers go on to sign a `mint_to` CPI with a bump taken from unverified vault state against a substituted mint.

Severity rationale
Impact high × Likelihood medium — The counterexample required no exotic state — all vault scalars were zero and every conceded assumption (program-owned vault, correct data length, real signer, real token program) is what an honest call looks like — so `load` accepts a substituted mint on the ordinary fee-deposit path, reachable by any caller who can present a vault buffer whose self-reported fields name the substituted accounts; the practical bar is obtaining/controlling such a vault account, which is made easier by the missing owner and discriminator checks in `VaultInfo::try_from`. Impact is high because the result is misrouted deposits and shares minted from an attacker-chosen mint under a program-signed CPI.
Impact
Deposited assets can be routed to an account the attacker controls rather than the canonical vault assets PDA, and shares can be issued from a substituted mint, with the `mint_to` CPI signed using a bump read from unverified vault state. This breaks the core guarantee that deposit handlers reject non-canonical vault asset/mint accounts and puts depositor funds and share accounting at risk.
Description
`rule_fee_deposit_does_not_rederive_shares_mint_pda` sets up a nondeterministic account array and a nondeterministic `Vault` that is self-consistent with the accounts passed (`v.shares_mint = *accounts[4].key`, `v.assets_mint = *accounts[3].key`, `v.vault_assets_account = *accounts[1].key`, `v.fee_token_account = *accounts[2].key`), concedes everything the property does not contest — `accounts[0].owner == &crate::ID`, exact `Vault` data length, `v.assets_mint != v.shares_mint`, a real signer, the real SPL Token program id, no asset-account aliasing — and then assumes the supplied `accounts[4].key` is *not* the address returned by the program's own `create_vault_shares_mint_address(accounts[0].key, &v)`. It asserts `DepositWithFeeContext::load(..).is_err()`. The Prover refuted it. The trace enters only `DepositWithFeeContext::load`, draws all six vault scalars as `0` (both bumps, `shares`, `assets`, `fee_bps`, `fee_amount`), and logs `ie: '0'` — i.e. `load` returned `Ok` — before the assertion at `fee_based_deposits.rs:611` fails. Nothing exotic was needed: none of those scalars is consulted on the validation path, so a zeroed vault buffer with a zero `vault_shares_mint_bump` is accepted just the same. The root cause is visible in the source. In `programs/vault/src/loaders/vault_with_fee_loaders.rs`, both PDA-bearing slots are declared as bare `AccountInfo<'info>` and are filled in `load` with `next_account_info(iter)?.clone()`. `validate` then performs exactly four comparisons — `vault.assets_mint == assets_mint.key`, `vault.shares_mint == shares_mint.key`, `vault.vault_assets_account == vault_assets_account.key`, `vault.fee_token_account == vault_fee_account.key` — and returns `Ok(self)`. There is no call to `create_vault_shares_mint_address`, no `VaultSharesMint::check_vault`, and no use of the `VaultSharesMint`/`VaultAssetsAccount` wrapper types anywhere on this path. `DepositContext::validate` in `vault_loaders.rs` types the same slot as `VaultSharesMint<'info>` and, after the identical `require_eq!`, calls `self.shares_mint.check_vault(self.vault_info.as_ref().key, &vault)?`, re-deriving `[SHARES_MINT, vault_pk, bump]` under `crate::ID`. The fee path simply omits that step for both PDA slots. Consequently `require_eq!(&vault.shares_mint, self.shares_mint.key, ..)` constrains nothing: both sides originate from caller-supplied input. The only gate before those comparisons is `VaultInfo::try_from` → `VaultInfo::validate` → `Vault::validate`, which enforces only `require_ne!(assets_mint, shares_mint)` — a condition every honest vault satisfies. Downstream (a source-level consequence, not something this trace executes), both `process_deposit_with_fee` and `process_deposit_with_fee_exact` read `vault_info.get()?.vault_shares_mint_bump` and pass `crate::vault_shares_mint_seeds_with_bump!(vault_info.as_ref().key, shares_mint_bump)` into `spl_mint_shares` against the unverified `shares_mint`, and similarly route the user's assets into the unverified `vault_assets_account` via `spl_transfer_assets_from_user`. Two halves of the evidence, stated explicitly: the counterexample proves `load` returns `Ok` on an account set constrained only by the vault's own self-reported fields; the fact that there is no derivation check at all to consult comes from reading `DepositWithFeeContext::validate`. The second half matters because the Solana Prover summarizes `Pubkey::create_program_address`, so the `expected` address the rule obtained is an unconstrained pubkey; read purely as a Prover artifact the rule would also fail against a program that *did* re-derive. The source reading settles the point that no such re-derivation exists. The same caveat attaches to the companion vault-assets-account rule, whose verdict is not covered here. A related trust-root gap compounds this: even with re-derivation added, the bump is read out of the `Vault` account, and `impl TryFrom<&AccountInfo> for VaultInfo` does not enforce `info.owner == &crate::ID` or check a discriminator before `bytemuck::from_bytes` interprets the data (its `// owned by vault program` / `// has discriminant` comments are unimplemented intentions). `VaultInfo::get` also slices `data[0..size_of::<Vault>()]` unconditionally and would panic on a short account.
Attack path
1. Attacker constructs a `Vault` account buffer (or supplies one it controls) whose `shares_mint` field holds the key of an attacker-chosen mint, whose `vault_assets_account` field holds an attacker-chosen token account, and with arbitrary (e.g. zero) `vault_shares_mint_bump` / `vault_assets_account_bump` — all balance and fee scalars may be zero. 2. The counterexample itself establishes only that `DepositWithFeeContext::load` returns `Ok` for a shares-mint account that is not the canonically derived PDA; the downstream exploitation (the `mint_to`/transfer CPIs signed with the unverified bump) is read from `process_deposit_with_fee` / `process_deposit_with_fee_exact`, not exhibited by this trace. Because the Prover summarizes `Pubkey::create_program_address`, the rule's `expected` address is unconstrained, so the trace alone cannot distinguish a missing check from an independent derivation — the claim that no derivation exists rests on direct reading of `DepositWithFeeContext::validate`, which contains no `check_vault` or `create_vault_shares_mint_address` call. The vault-assets-account half of the property is asserted from the same source reading; its companion rule's verdict was not provided. Description

rule rule_update_reward_preserves_fee_backing in reward_accounting.rsprover run

Impact high × Likelihood low — Impact is high because the double count permanently desynchronizes recorded assets from custodied tokens: after `collect_fee` the vault claims more assets than it holds, over-valuing shares and leaving redemptions unpayable. Likelihood is low only because the triggering state (`fee_amount > 0`) is not reachable in the current snapshot — no handler increments that field today — even though the reward-sync instruction itself is permissionless and callable by any actor once fee accrual is enabled.
Impact
Pending protocol fees are recognized a second time as shareholder reward, inflating `vault.assets` to the full token balance while `fee_amount` remains owed. A subsequent `collect_fee` then moves those same tokens out of the asset account without reducing `vault.assets`, leaving the vault recording more assets than it custodies — shares are over-valued and the last redeemers cannot be paid in full. This is a direct accounting/solvency defect affecting user funds, not merely a cosmetic deviation.
Description
The vault's asset token account is the custody account for two distinct claims: the shareholder claim tracked in `vault.assets`, and the pending protocol fee tracked in `vault.fee_amount`. The state type already encodes this: `Vault::gross_assets()` is defined as `assets + fee_amount` precisely because both are backed by the same pot, and `vault_collect_fee` transfers `fee_amount` tokens out of that same account. `vault_update_reward` (programs/vault/src/operations/vault_operations.rs) is the single place in the program that reconciles recorded state against the real on-chain balance, and it reconciles against the wrong quantity: ```rust let reward = new_amt .checked_sub(vault.num_assets()) .ok_or(VaultError::MathOverflow)?; if reward > 0 { vault.add_token(reward)?; } ``` Only `vault.assets` is deducted. Any tokens sitting in the account to back an uncollected fee are therefore treated as surplus — i.e. as reward — and credited to shareholders via `add_token`. The result is a double count: the same tokens now back both `vault.assets` and `vault.fee_amount`. `rule_update_reward_preserves_fee_backing` formalizes the backing invariant. On a well-shaped, program-owned vault state account and a 165-byte `spl_token`-owned asset account with distinct keys, it assumes `vault.assets + vault.fee_amount <= balance(vault_assets_account)` at entry, calls `process_update_reward` with `.unwrap()` (so only successful executions are covered), and asserts the same inequality afterwards. The Prover produced an execution where it fails, at reward_accounting.rs:329. In the counterexample the entry state is `a0 = vault.assets = 4808`, `f0 = vault.fee_amount = 1`, and a token balance `bal0` that comfortably satisfies `4808 + 1 <= bal0` (the solver happened to pick a very large `u64` near `u64::MAX`; the magnitude is incidental). `UpdateRewardContext::load` and `spl_token_account_amount` both complete, the handler returns `Ok`, and no transfer occurs — `bal1 == bal0`. The post-state is `a1 == bal1` (assets inflated to the entire token balance) with `f1 = 1` unchanged, so the postcondition degenerates to `bal0 + 1 <= bal0` and fails. The break is structural rather than an artifact of the chosen witness: whenever the handler succeeds with `fee_amount > 0` and a strictly positive reward, `assets` is set to the full balance while the fee claim remains outstanding, so `assets + fee_amount <= balance` cannot hold. Notably this is not an arithmetic overflow — both `checked_sub` and `checked_add` succeed; the subtraction simply uses the wrong operand. It is also invisible to the program's own `Vault::check_invariant`, which only checks `shares <= assets` and is unaffected because `assets` only grows here. The downstream consequence is a solvency gap: once the admin calls `collect_fee`, `fee_amount` tokens leave the asset account while `vault.assets` is not reduced, leaving the vault recording more assets than it actually holds, so not all redemptions can be honoured. Note also that the related Property 1 formulation — "after a successful call, `vault.assets` equals exactly the token balance" — is itself a symptom of the same omission; it is only correct while `fee_amount == 0` and would need restating in gross form (`assets + fee_amount == balance`) once the handler is fixed. Recommended fix: compute the reward against all outstanding claims, i.e. `new_amt.checked_sub(vault.gross_assets())` instead of `new_amt.checked_sub(vault.num_assets())`. This recognizes only the genuine surplus, keeps the pending fee backed, and has the useful side effect that a balance below `assets + fee_amount` now fails `checked_sub` and returns `MathOverflow`, which is the correct response to a real shortfall. More broadly, every comparison of the asset account's balance against recorded state should use `gross_assets()`.
Attack path
1. The vault holds a non-zero pending fee in `vault.fee_amount` (counterexample: `fee_amount = 1`, `assets = 4808`), backed by tokens sitting in `vault_assets_account` alongside the shareholder assets; the backing invariant `assets + fee_amount <= balance` holds. 2. Anyone calls the reward-sync instruction, `process_update_reward`. The handler loads the context, reads the real token balance via `spl_token_account_amount`, and computes `reward = balance - vault.assets` — which includes the tokens earmarked for the pending fee. 3. `vault.add_token(reward)` credits that amount to shareholders. The post-state is `vault.assets == balance` with `vault.fee_amount` still outstanding; the backing invariant is now violated (`assert FAIL` at reward_accounting.rs:329). 4. The admin later calls `collect_fee`, which transfers `fee_amount` tokens out of `vault_assets_account` and clears the counter without reducing `vault.assets`. The vault now records more assets than it holds, and redemptions can no longer all be honoured.
Assumptions & uncertainties
The counterexample requires `vault.fee_amount > 0` at entry. In the exact code snapshot audited, no handler ever *increases* `vault.fee_amount` — the only writer is `Vault::clear_fee_amount` called from `vault_collect_fee`, and the fee-based deposit paths route fees to a separate fee token account rather than crediting the counter. The defect in `vault_update_reward` is therefore real at the code level but latent as an exploit against this snapshot; it becomes live as soon as fee accrual onto `vault.fee_amount` is wired up, which the existence of the field, `gross_assets()` and `collect_fee` all plainly anticipate. The rule's only assumptions beyond account shape, key distinctness and realistic ownership are the entry backing invariant itself, so nothing in the harness manufactures the failure.

An attacker can inflate `vault.assets` to an arbitrary value by passing a forged, token-account-shaped account to `update_reward`, causing the vault to recognize phantom reward it never received. Since share price and subsequent redemption accounting are derived from `vault.assets`, this corrupts the vault's core accounting: attacker-held shares can be valued against assets that do not exist, enabling over-redemption against the real asset reserve and leaving the vault insolvent for remaining depositors. The absence of the SPL Token owner check means the "balance" need not come from any real token account at all.
Description
`process_update_reward` reads the vault's asset balance by unpacking SPL token account bytes from the account passed at index 1 and recognizing any surplus over `vault.assets` as reward. The only validation performed on that account is in `UpdateRewardContext::validate`: ```rust require_eq!(&vault.vault_assets_account, self.vault_assets_account.key, ProgramError::InvalidArgument); ``` This check is self-referential. The right-hand side is the key of whatever account the caller chose to pass; the left-hand side is a field read out of the vault state account's bytes. It therefore proves only "you passed the account the record names" — never "this account is the program's canonical `create_program_address([VAULT_ASSETS, vault_pk], vault.vault_assets_account_bump)` PDA". Two structural omissions make this exploitable: 1. **No PDA re-derivation.** `UpdateRewardContext` declares the field as a bare `AccountInfo<'info>` rather than the `VaultAssetsAccount<'info>` newtype used by `DepositContext` and `SlashContext`, and loads it with `next_account_info(iter)?.clone()`, bypassing the `TryFrom` path. Because of the field type, `check_vault` — which re-derives the address and compares — is not even reachable, and `UpdateRewardContext::validate` omits the call that both sibling contexts make. 2. **No owner check.** `spl_token_account_amount` is just `spl_token::state::Account::unpack(&info.try_borrow_data()?)`. `Pack::unpack` validates the data length, the `COption` tags and `is_initialized` — it never inspects `info.owner`. So any account whose bytes happen to be shaped like an initialized SPL token account is accepted, regardless of which program owns it. The counterexample makes the break concrete. The asset account key is `0xc3ff...` while the program's own derivation returns a different value, so the antecedent "non-canonical asset account" genuinely holds on this path. `UpdateRewardContext::load` completes without error, `spl_token_account_amount` → `unpack_from_slice` runs on the forged account, and the handler returns `Ok` (`r.is_err(): '0'`). Critically, the handler does not merely accept the account passively: `v0.num_assets()` is 4,612 before the call and `v1.num_assets()` is `0x300000079` after it, while `num_shares` is unchanged at 9,605. The handler read a balance out of the attacker-supplied account, computed a strictly positive reward, and persisted an attacker-chosen `vault.assets` into the vault record. One caveat on the strength of the witness, which does not weaken the conclusion: the build summarizes `Pubkey::create_program_address`, so the derived `expected` address printed as `'0'` is unconstrained and is not a plausible real on-chain PDA. What the trace establishes rigorously is the structural fact that is the entire content of the property — the handler's acceptance is independent of *any* program-address derivation, because none is performed anywhere on its path. Under the summary, `expected` could have been any value and the handler would still have returned `Ok`, since no code reads it. The secondary observation — `vault.assets` changing after `unpack_from_slice` ran on the forged account — does not depend on the summary at all and is what demonstrates the consequence. The exposure is compounded by a related gap the analysis flags: `VaultInfo::try_from` carries the comments `// owned by vault program` and `// has discriminant` but implements neither, performing only `Vault::validate` (`require_ne!(assets_mint, shares_mint)`). This means `vault.vault_assets_account` and `vault.vault_assets_account_bump` — the very inputs a re-derivation would use — can themselves be attacker-chosen, so adding the derivation alone would not be sound without also fixing the vault-account owner and discriminant checks.
Attack path
1. The attacker constructs (or reuses) an account whose data is shaped like an initialized SPL token account — correct length, valid `COption` tags, `is_initialized` set — and whose `amount` field encodes an arbitrarily large balance. Because `spl_token_account_amount` calls `Pack::unpack` without consulting `info.owner`, this account need not be owned by the SPL Token program. 2. The attacker supplies a vault state account whose `vault_assets_account` field holds the key of that forged account. `VaultInfo::try_from` enforces neither program ownership nor a discriminant, and `Vault::validate` only requires `assets_mint != shares_mint`, so the record is accepted. 3. The attacker invokes `update_reward` with these two accounts. `UpdateRewardContext::load` takes the asset account via `next_account_info(iter)?.clone()` as a bare `AccountInfo`, so `check_vault` is never reachable and no PDA is re-derived. 4. `UpdateRewardContext::validate` runs its single `require_eq!(&vault.vault_assets_account, self.vault_assets_account.key, ...)`, which passes trivially because both sides trace back to the attacker's own inputs. 5. The handler unpacks the forged balance, computes the surplus over the stored `vault.assets` as recognized reward, and persists the inflated value — in the trace, `num_assets` goes from 4,612 to 0x300000079 with `num_shares` unchanged at 9,605, so the handler returns `Ok` with corrupted vault accounting.
Assumptions & uncertainties
The counterexample was produced under a build that applies a default points-to summary to `Pubkey::create_program_address`, so the derived address printed as `'0'` is unconstrained and the specific pubkey values in the trace are not plausible real on-chain addresses. The violation therefore proves the structural absence of any address derivation on the handler's path rather than a concrete mismatch against a real PDA; this is sufficient, since no code on the path reads the derived value at all. The `vault.assets` corruption observed in the trace does not depend on the summary. The write-up assumes the standard vault economics in which `vault.assets` feeds share-price and redemption math; the exact downstream loss magnitude depends on the redemption logic, which was not part of this rule. Step 2 of the attack path relies on the separate missing owner/discriminant checks in `VaultInfo::try_from` (the subject of the companion Property 8 rule); even without forging the vault record, the missing owner check in `spl_token_account_amount` remains independently exploitable against whatever account the legitimate record names if that account is ever not a genuine SPL token account. Recommended remediation, per the analysis: (1) type the field as `VaultAssetsAccount<'info>` and load it via `try_into()`; (2) add `self.vault_assets_account.check_vault(self.vault_info.as_ref().key, &vault)?` to `UpdateRewardContext::validate`; (3) add `require_eq!(info.owner, &spl_token::id(), ProgramError::IllegalOwner)` inside `spl_token_account_amount` before the unpack, so every caller inherits it; (4) add the missing `crate::ID` owner check and discriminant check to `VaultInfo::try_from`, plus a length guard before the `data[0..size_of::<Vault>()]` slice in `get`/`get_mut`, which panics on a short account today.

medium SlashContext::validate never binds the passed vault_assets_account to the vault's recorded pubkey, allowing a slash to drain an unrelated PDA

rule rule_slash_assets_account_matches_recorded_pubkey in slashing.rsprover run

`SlashContext::validate` only re-derives the assets account from `["assets", vault_pk, vault.vault_assets_account_bump]` via `check_vault`, and — unlike `DepositContext`, `RedeemSharesContext` and `UpdateRewardContext` — never compares the passed account to the `vault.vault_assets_account` field stored in vault state. The Certora Prover produced an accepted `process_slash` execution in which `accounts[1].key` (`0xfa6f…`) differs from the vault's recorded `vault_assets_account` (`0x27b2…`), so a slash can move tokens out of a PDA that is not the vault's recorded asset account while debiting this vault's recorded `assets`.

Severity rationale
Impact high × Likelihood low — The counterexample proves `SlashContext::validate` imposes no constraint whatsoever linking `accounts[1].key` to `vault.vault_assets_account`, and the accepted trace needs no particular balance (`amount = 0`), so the missing check is trivially reachable. However, exploitation requires the `slash_admin` signer and a vault whose stored bump is non-canonical or inconsistent with its stored asset-account pubkey, which is a privileged and non-default configuration — hence low likelihood with high impact if it obtains.
Impact
A slash can be executed against a token PDA that is not the vault's recorded asset account: the program signs the transfer with validated vault seeds and simultaneously debits the invoking vault's recorded `assets` balance. This produces token movement out of an account the vault never recorded plus corrupted internal accounting (recorded assets reduced without the corresponding recorded account being touched), i.e. loss of funds from an unrelated program-controlled asset account and divergence between on-chain balances and vault state.
Description
The rule `rule_slash_assets_account_matches_recorded_pubkey` asserts that for any successful execution of `crate::processor::process_slash`, the account supplied in slot 1 must equal the pubkey the vault state records in `vault.vault_assets_account`. The pre-state vault is read out of `accounts[0]` before the call, and the handler is driven directly with `.unwrap()`, so only executions the program actually accepts reach the assertion. The Prover returned a concrete accepted execution that refutes it: `amount = 0`, the account in slot 1 has key `0xfa6f…` (`vault_assets_account_key_lo64 = 255`), the vault state records `vault_assets_account = 0x27b2…` (`vault.vault_assets_account_lo64 = 0`), and the derived flag `key_matches_record` is `0`. The call chain descends `process_slash` → `SlashContext::load` → `SlashContext::validate` and returns `Ok`, so validation passed with two genuinely distinct pubkeys. The root cause is visible directly in the source and does not depend on how the Prover models PDA derivation. In `programs/vault/src/loaders/vault_loaders.rs`: - `DepositContext::validate` performs **both** `require_eq!(&vault.vault_assets_account, self.vault_assets_account.as_ref().key, ProgramError::InvalidArgument)` and `self.vault_assets_account.check_vault(vault_pk, &vault)`. - `RedeemSharesContext::validate` and `UpdateRewardContext::validate` each perform the `require_eq!` against `vault.vault_assets_account`. - `SlashContext::validate` performs **only** `self.vault_assets_account.check_vault(vault_pk, &vault)?` (the `Pubkey::create_program_address(["assets", vault_pk, vault.vault_assets_account_bump], &crate::ID)` re-derivation) plus the `slash_admin` comparison. These two checks are not equivalent. `check_vault` relates the passed account to `(vault_pk, stored bump)` and to nothing else; the stored `vault.vault_assets_account` pubkey is an independent field of the same `Vault` struct, and nothing ties the two together — `Vault::validate` asserts only `assets_mint != shares_mint`. Consequently, on the slash path there is **no constraint at all** relating `accounts[1].key` to `vault.vault_assets_account`. For a vault whose stored bump is non-canonical or has drifted from (or was never made consistent with) its stored asset-account pubkey, a slash signs with the vault-derived seeds and transfers tokens out of a PDA that is not the vault's recorded asset account, while the accounting debit (`del_token`) is applied to this vault's recorded `assets`. The same function is additionally missing the `require_eq!(&vault.assets_mint, self.assets_mint.key, ...)` that `DepositContext` and `RedeemSharesContext` perform; that omission is tracked by a separate rule but should be repaired in the same place. Remediation — in `SlashContext::validate`, restore parity with the other contexts: ```rust require_eq!( &vault.vault_assets_account, self.vault_assets_account.as_ref().key, ProgramError::InvalidArgument ); self.vault_assets_account.check_vault(vault_pk, &vault)?; ``` A deeper fix is to establish the consistency between `vault.vault_assets_account` and `vault.vault_assets_account_bump` once at vault initialization and assert it in `Vault::validate`, so `check_vault` and the `require_eq!` can never disagree in any context.
Attack path
1. A vault exists (or is created) whose stored `vault_assets_account_bump` is non-canonical or otherwise inconsistent with the stored `vault.vault_assets_account` pubkey — nothing in `Vault::validate` or initialization forbids this. 2. The `slash_admin` invokes `process_slash`, passing in account slot 1 a token PDA that derives from `["assets", vault_pk, vault.vault_assets_account_bump]` but is **not** the pubkey recorded in `vault.vault_assets_account`. 3. `SlashContext::validate` runs `check_vault` (which succeeds on the seed re-derivation) and the `slash_admin` comparison, and returns `Ok` — no `require_eq!` against the recorded field exists on this path. 4. `process_slash` signs with the vault-derived seeds, moves tokens out of the non-recorded PDA, and debits the recorded `assets` of this vault. 5. Counterexample witness: slot-1 key `0xfa6f…` (lo64 = 255) vs. recorded `vault.vault_assets_account = 0x27b2…` (lo64 = 0), `key_matches_record = 0`, handler returned `Ok`.
Assumptions & uncertainties
The only assumption in force in the rule is `accounts[0].data_len() == size_of::<Vault>()`. `Pubkey::create_program_address` is modelled by the Prover rather than computed, so the specific witness pubkeys (`0xfa6f…`, `0x27b2…`) are not a ready-made on-chain exploit pair; what the trace establishes independently of that model — and what is directly visible in the source — is that no constraint relates `accounts[1].key` to `vault.vault_assets_account` on the slash path. Realizing the gap on-chain requires a vault whose stored bump and stored asset-account pubkey are inconsistent; whether current initialization code can produce such a vault was not established by this rule, so the practical exploit depends on that (or on any future path that writes these fields independently). The witness uses `amount = 0`, which is incidental — it merely shows the shortest accepted path needs no vault balance.

rule rule_slash_assets_mint_matches_vault_record in slashing.rsprover run

`process_slash` accepts an arbitrary account in the `assets_mint` slot (account index 3): `SlashContext::load` reads it as a bare `AccountInfo` and `SlashContext::validate` checks only `slash_admin` and the vault assets account, omitting the `require_eq!(&vault.assets_mint, self.assets_mint.key, ...)` that `DepositContext` and `RedeemSharesContext` both perform. The Prover produced an accepting slash execution in which the passed mint (`..01e000ea`, lo64 `234`) differs from the vault's recorded mint (`..01e00109`, lo64 `9`).

Severity rationale
Impact low × Likelihood high — The counterexample reaches acceptance on an ordinary slash with `amount = 2` and no exotic vault state, and the missing `require_eq!` is visible directly in `SlashContext::validate`, so anyone able to invoke slash can supply a mismatched mint — hence high likelihood. Impact is low because the unvalidated `_mint` is currently discarded by the non-decimals-aware SPL `transfer`, so no funds are at risk today; the issue is a latent account-binding gap and a misrepresented account list rather than an exploitable theft path.
Impact
The slash instruction's `assets_mint` account is entirely unconstrained: a caller can present any mint account in that slot and the program will accept the slash and emit a transfer. No funds are lost today because the parameter is discarded by the non-decimals-aware `spl_token::instruction::transfer`, but the instruction's account list misrepresents which mint the vault operates on — misleading explorers, off-chain indexers and any consumer that trusts the slot — and the gap becomes directly exploitable the moment the mint is honoured (e.g. a migration to `transfer_checked` or decimals derived from the supplied account), since the value read would then be attacker-chosen.
Description
The rule `rule_slash_assets_mint_matches_vault_record` drives the real `crate::processor::process_slash` handler over unconstrained `AccountInfo`s, assuming only that `accounts[0]` has the exact byte length of a `Vault`, and asserts that any accepted execution satisfies `*accounts[3].key == vault.assets_mint` (the vault state read from the pre-state). Neither inspects `assets_mint`. The only other mint-related code on the path, `Vault::validate` (reached via `VaultInfo::try_from`), asserts only that the two *stored* fields `assets_mint != shares_mint`; it says nothing about the account supplied by the caller. The scope of the break should be stated precisely. The counterexample establishes that the mismatch is *accepted*; it does not exhibit a loss of funds. Any change that begins honouring it — a switch to `transfer_checked`, deriving decimals from it, or an off-chain consumer trusting the account list — converts the gap into a live bug, because the value read would be attacker-chosen. Remediation: add the comparison the sibling contexts already perform to `SlashContext::validate`: ```rust require_eq!( &vault.assets_mint, self.assets_mint.key, ProgramError::InvalidArgument ); ``` Since slash writes only the `assets` field, the pre-state read the rule performs is the right one to compare against, and this single check makes the asserted property hold on every accepting execution. Structurally, giving `assets_mint` the same newtype-with-`check_vault` treatment that `VaultAssetsAccount` and `VaultSharesMint` already receive would make binding the default rather than something each context must remember, closing this whole class of omission.
Attack path
1. An actor invokes `process_slash` with the vault account in slot 0 and an attacker-chosen mint account (key `0x1000…01e000ea`, lo64 `234`) in slot 3, while the vault records `assets_mint = 0x1000…01e00109` (lo64 `9`). 2. `SlashContext::load` reads slot 3 via a bare `next_account_info(iter)?.clone()` into a plain `AccountInfo`, with no `TryFrom` validation hook. 3. `SlashContext::validate` checks only `vault.slash_admin == authority.key` and `vault_assets_account.check_vault(...)`; it never compares slot 3 to `vault.assets_mint`. 4. Validation succeeds and `process_slash` passes the unvalidated account into `spl_transfer_assets_from_vault` as `_mint`, returning `Ok` with `amount = 2` — the handler accepts an execution where `*accounts[3].key != vault.assets_mint` (`mint_matches_record = 0`).
Assumptions & uncertainties
The diagnosis is not uncertain: the omitted `require_eq!` is visible in the source, the trace confirms the path reaches `SlashContext::validate` and returns successfully, and the two logged `_lo64` values confirm the keys genuinely differ; the assertion compares two ordinary stored/passed pubkeys and depends on no PDA derivation, CPI modelling, or summarized function. The low impact rating assumes the current implementation, where `spl_token::instruction::transfer` ignores the `_mint` parameter; if the program migrates to `transfer_checked`, derives decimals from the supplied mint, or if off-chain consumers trust the account list, the severity rises because the attacker controls the value read. The rule itself is correctly stated and marked `expect_rule_failure`; it should not be weakened or inverted, and the marking should be withdrawn only once the loader is repaired.
