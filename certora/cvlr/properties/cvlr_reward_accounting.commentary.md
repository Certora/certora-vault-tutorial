## What the harness does

`process_update_reward` is a native (non-Anchor) handler, `fn(accounts: &[AccountInfo]) -> ProgramResult`, with no non-account arguments: the "new amount" of the component description is *read* from the vault asset token account, not passed in. Account order is `0 = vault_info` (zero-copy `Vault`), `1 = vault_assets_account`.

**All twelve rules drive the real handler**, `crate::processor::process_update_reward`. Nothing is reimplemented: `UpdateRewardContext::load` (and through it `VaultInfo::try_from`, `Vault::validate` and the `require_eq!` on `vault.vault_assets_account`), the real `spl_token_account_amount`, and the real `crate::operations::vault_update_reward` are all inside every proof. The harness contributes only observation helpers — `read_vault` is a zero-copy `bytemuck::from_bytes` over the same bytes `VaultInfo::get` casts, `prog_token_amount` wraps the program's own `spl_token_account_amount`, and the canonical-PDA rule uses the program's own `crate::state::create_vault_assets_account_address`.

The only modelling is account *shape*: `cvlr_assume!(data_len == size_of::<Vault>())` on account 0 and `== spl_token::state::Account::LEN` on account 1, plus distinct keys. A nondeterministic account has a nondeterministic data length, which neither `bytemuck::from_bytes` nor `Pack::unpack` can be analyzed against. Every other byte of both accounts is unconstrained.

No summaries were added, no munges were applied, `optimistic_loop` is off, the loop bound is the default 2, and no lemma was used.

## Results

Seven rules VERIFIED (Properties 1–6 and 11). Five rules are VIOLATED and are marked expected-failure: they are the four attack-vector properties (7, 8, 9, 10), with Property 9 carrying two rules, one per conjunct. Each is a confirmed defect in the shipped code, not a defect in the rule; the justifications are recorded with the markings. Three of the five witnesses show not merely acceptance but a *write*: the foreign-owned-vault, foreign-owned-asset-account and non-canonical-asset-account traces each have `v1.num_assets()` differing from `v0.num_assets()`, so the handler decoded a caller-chosen balance and credited a reward into the vault record.

## Scoping a reader needs in order to trust the verdicts

**Success-path scoping.** Rules 1, 3, 4, 5, 6, 7 and 10 consume the handler's `Result` with `.unwrap()`, so they cover successful executions only. This is sound on Solana: an `Err` aborts the instruction and the runtime rolls back every account mutation, so a failing path leaves no state for an invariant to be false about. Rule 2 separately checks the no-write-on-error case for the balance-below-assets path, asserting all twelve `Vault` fields unchanged.

**The ownership assumptions.** Rules 1, 3, 4, 5, 6, 7, 10 and 11 assume, via `assume_real_owners!`, the two facts the handler does *not* check: `vault_info.owner == crate::ID` and `vault_assets_account.owner == spl_token::id()`. Those verdicts therefore describe honest-account executions. The handler's failure to enforce either is exactly what rules 8 and 9(a) report, so the two readings are complementary rather than in tension.

**Property 1 — the oracle.** The balance the rule compares `vault.assets` against is produced by the program's own `spl_token_account_amount`, i.e. a wrapper over `spl_token::state::Account::unpack(..).amount` — the canonical SPL decoder, not harness arithmetic and not a separate token model that could disagree with what the handler reads. The rule asserts equality against the balance read both before and after the call.

**Property 5 — what is and is not proved.** The rule does **not** establish the "performs no CPI" conjunct, and should not be read as doing so: the Prover's model of `invoke`/`invoke_signed` moves no value, so a post-state "balance and lamports unchanged" assertion cannot distinguish a handler that CPIs from one that does not. What the rule proves is that a successful call writes nothing to the asset account's decoded `amount`, nothing to the three sampled bytes (offsets 0, 108 and 164 — the data check is at those offsets plus the decoded amount, not over all 165 bytes), and changes the lamports of neither passed account. The absence of a CPI is a source-level fact — `process_update_reward` contains no `invoke`/`invoke_signed`, and `vault_update_reward` returns `VaultEffect::default()` — and is cited as such, not as a verdict.

**Property 7 — real but latent in this snapshot.** The code-level defect is unambiguous: `vault_update_reward` subtracts `vault.num_assets()` where `Vault::gross_assets()` (`assets + fee_amount`) is the quantity the token account actually backs, so a positive reward recognizes pending fees as shareholder reward and a later `collect_fee` leaves the vault recording more assets than it holds. Its exploitability *today* is latent, however: no handler in the current program ever increases `vault.fee_amount` — the only writer of the field is `Vault::clear_fee_amount` in `vault_collect_fee`, and the fee-based deposit paths route the fee to the separate fee token account rather than crediting the counter. The counterexample's `f0 = 1` entry state is therefore not reachable through this snapshot's instructions. Report it as a defect that bites as soon as fee accrual onto `vault.fee_amount` is wired up — which the field, `gross_assets()` and `collect_fee` all plainly anticipate. Note also that Property 1's "assets equals exactly the balance" formulation is itself a symptom of the same omission: under the corrected handler the post-state would be `assets + fee_amount == balance`, so a green Property 1 should not be read as endorsing the current arithmetic.

**Property 9(b) — the `create_program_address` caveat.** The build applies a default points-to summary to `Pubkey::create_program_address`, so the `expected` address the rule derives through the program's own helper is unconstrained and is not pinned to the true PDA. The counterexample's "key != expected" is therefore not by itself evidence of non-canonicity. What the violation establishes rigorously is the structural fact: acceptance is independent of *any* address derivation, because `UpdateRewardContext::validate` performs none — its only guard is the self-referential `require_eq!(&vault.vault_assets_account, key)`, read out of the same (possibly forged) vault bytes. The secondary observation in the same trace — `vault.assets` changing after `unpack_from_slice` ran on the non-canonical account — does not depend on the summary. The 9(a) owner conjunct is fully checkable and produces a clean, unqualified counterexample.

**Property 10 — scope of the finding.** The rule pins `shares == 0` **and** `assets == 0` at entry, so what it reports is the handler *creating* the terminal state from a freshly initialized vault rather than finding it already present; the `shares == 0, assets > 0` entry state is not covered (and is already bricked). The witness is legible — a donated balance of 3 takes the vault to `(shares = 0, assets = 3)`. The bricking argument depends on `Vault::convert_assets_to_shares` taking its `mul_div_floor` branch: with `shares == 0 < assets` the `shares == assets` 1:1 passthrough does not fire, so the conversion returns 0 and `mint_shares`'s `require_gt!(amt, 0)` rejects every deposit, while no shares exist to redeem.

**Property 11 — domain of the acceptance result.** The rule is universal, not a satisfy rule: for *every* program-owned vault with `assets_mint != shares_mint`, no signer among the accounts, and a token account holding strictly more than the vault records, it asserts `r.is_ok()` and `assets_after == balance`. Two domain restrictions should be read with it. The asset account's *key* is pinned to `vault.vault_assets_account` — the equality the handler actually checks — and not to the canonical PDA, for the same `create_program_address` summary reason as 9(b). And the domain is token accounts that unpack: the four `COption` tags and the `state` byte are pinned to a shape `Pack::unpack` accepts (mint, owner field, `amount` and `delegated_amount` all stay unconstrained), and `prog_token_amount`'s `unwrap` prunes the rest. So the result reads "the permissionless reward path is live and exact for well-formed token accounts", not as a canonicity claim.

## Recommended fixes, consolidated

1. `VaultInfo::try_from` — add `require_eq!(info.owner, &crate::ID, ProgramError::IllegalOwner)` and the account discriminant its own comments promise, plus a length guard before `bytemuck::from_bytes`. This closes Property 8 for every handler that loads the vault.
2. `spl_token_account_amount` — check `info.owner == &spl_token::id()` before `unpack`; `Pack::unpack` validates length, the `COption` tags and `is_initialized`, never the owner. This closes Property 9(a) for every caller.
3. `UpdateRewardContext` — type `vault_assets_account` as `VaultAssetsAccount<'info>` and call `check_vault(vault_pk, &vault)`, as `DepositContext` and `SlashContext` do. This closes Property 9(b).
4. `vault_update_reward` — subtract `vault.gross_assets()` rather than `vault.num_assets()`. This closes Property 7 and makes the shortfall rejection condition correct.
5. `vault_update_reward` or `convert_assets_to_shares` — either refuse to credit a reward when `vault.num_shares() == 0`, or give the deposit path a bootstrap branch so the `shares == 0, assets > 0` state is recoverable. This closes Property 10; note that the first option makes Property 11's acceptance claim conditional on `shares > 0`.
